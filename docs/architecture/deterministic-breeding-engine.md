# Phase 4 确定性配种搜索与综合评分设计

- 状态：实现与 BLOCKER/HIGH 自动化门禁已通过，待真实数据人工验收
- 日期：2026-07-14
- 算法事实源：固定 published `game_data_version_id + content_hash` 中的目录事实，以及固定 `inventory_snapshot_id + world_id` 中的库存事实
- 需求来源：`docs/superpowers/specs/2026-07-13-palworld-breeding-system-design.md`

## 1. 边界与现状

本模块实现 Phase 4 的确定性配种引擎及其精确事实 Adapter。AI 不在输入、索引、搜索、实例分配或评分接口中出现，也不能新增配方、改变配方优先级、修改基础分数或覆盖候选顺序。

现有代码提供了以下可复用边界：

- `LoadedGameCatalog` 按精确 `game_data_version_id` 加载不可变目录，其中包含普通和特殊 `CatalogBreedingRecipe`。
- 配方父母在导入时按稳定英文 ID 无序归一化；现有 `resolve_breeding_child` 已定义同一父母对的特殊配方优先语义，但尚无搜索索引。
- `breeding_jobs` 已固定库存快照、统一游戏数据、算法和评分配置版本。
- Phase 3 库存发布保留性别、被动、所有者、公会、位置，并在筛选后的 `raw_metadata` 中记录 `resolution_status/shared_eligible`；共享偏好按实例 UID 独立保存。
- `BreedingEngineAdapter` 从已领取 Job 固定版本，Repository 只加载该 UUID 的 published 元数据、目录制品和该 Job 固定的库存 envelope；UUID、content hash、world 或 snapshot 任一不一致即稳定失败。
- 数据库启动注册表提供四套 `phase4b-deterministic-v1/*-v2` 七项权重；Adapter 启动时逐项与代码整数基点注册表核对，不一致则 fail closed。
- 库存投影显式提供 `breeding_enabled`、`plan_locked`、共享和解析布尔值，引擎不从原始 metadata 猜测。
- 当前目录没有经过验证的精确被动继承概率。因此结果只给出低/中/高难度和策略性尝试次数区间，不输出成功概率。

本阶段不修改真实存档、不访问生产数据库、不自动发布目录版本、不接入 AI，也不自动推进计划。本地集成测试只验证真实 Supabase Claim → Adapter → Engine → Worker 完成链路。

## 2. 共享输入与输出契约

新增单一 JSON Schema 作为 TypeScript 和 Python 的共同来源。

输入固定：

```text
target_pal_id
desired_passive_ids（排序去重后 0～4 个）
world_id
inventory_snapshot_id
game_data_version_id
game_data_content_hash
algorithm_version
scoring_profile_version
optimization_mode
requester_player_id / requester_guild_id
allow_shared_inventory / allow_locked_reuse
固定快照中的实例及共享、解析、禁用、锁定状态
搜索限制（代数、展开节点、超时、内部候选上限、输出上限）
```

配方不复制进请求 DTO。引擎只接受 `VersionedBreedingCatalog` 与 `FixedInventorySnapshot` 组成的 `BreedingRuntimeFacts`，裸配方列表不能伪装成声明版本。结果回显所有固定版本及目录 content hash，并包含：

- 稳定 `route_key`、请求模式下的排名和四种模式的确定性分数。
- 按拓扑顺序排列的步骤、有效配方类型、真实起始实例和中间代引用。
- 每个中间代必须保留的被动、后续需要的性别、借用信息和位置。
- 难度、策略尝试次数区间、库存覆盖、借用数和完整 `score_breakdown`。
- 搜索规模、展开/剪枝计数、是否穷尽、命中的限制和稳定解释码。
- 对不含运行时耗时/内存的规范结果计算 SHA-256 摘要。

## 3. 合法配方索引

构建索引时再次对父母 ID 排序，不信任调用方顺序。索引同时保存：

```text
(parent_low, parent_high) -> 唯一有效配方
child_pal_id -> 有序的有效配方列表
```

同一父母对的规则：

1. 若存在特殊配方，只把特殊配方放入有效索引，普通配方成为被覆盖事实，绝不进入路线。
2. 否则使用普通配方。
3. 同类型出现多个不同子代时返回稳定 `BREEDING_RECIPE_CONFLICT`，不任意选择。
4. 所有步骤在输出前再次通过父母索引验证；索引外关系不能序列化为候选。

## 4. 两层搜索

### 4.1 种类路线

种类路线是由库存叶节点和配种步骤组成的不可变二叉树。内部节点只引用有效配方；树高是代数，步骤数是内部节点数。库存中已经存在完全满足目标的实例可形成 0 代路线。

搜索先从目标反向计算最大代数内相关的配方闭包，再从候选库存种类正向构造可执行路线：

1. 第 0 代为候选库存中存在的种类。
2. 第 `g` 代只组合已在 `< g` 代可达的父母路线，并要求新路线树高恰为 `g`。
3. 路线签名包含有效配方和两个父路线签名；相同父种类时按签名归一化。
4. 每个子代保留有界的最优结构状态，排序键依次考虑代数、步骤数、叶节点数和稳定签名；被动与实例只在第二层参与可行性和评分。
5. 循环只能产生代数更高的有限树；最大代数、签名去重和状态上限共同保证终止。

小图穷举 Oracle 使用独立、无启发式裁剪的逐代组合器。属性测试在未命中限制的小图上比较优化搜索和 Oracle 的完整路线签名集合。

### 4.2 真实实例分配

种类路线通过后，以动态规划给每个库存叶节点分配真实实例：

- 配种步骤的两个父母必须一公一母；`unknown` 和 `genderless` 不能作为配种父母。
- 中间子代若在后续作为父母，则路线记录必须获得的性别，并把额外筛选成本计入尝试区间。
- 根节点为 0 代库存直达时可使用任意已解析性别，因为它不参与本路线的配种步骤。
- 同一步骤不允许同一实例同时充当两个父母；跨顺序步骤默认可复用未锁定实例。
- 同种父母只枚举一个稳定性别方向；候选上限和评分前再按与左右父槽位无关的物理计划签名去重，镜像不会被计作两条路线。
- 状态按“已覆盖期望被动位图”分桶，只在同一覆盖集合内按借用、额外被动和稳定实例 UID 做支配剪枝，避免把唯一可覆盖组合剪掉。

候选池过滤顺序固定并记录计数：

1. 不在固定快照中：`INVENTORY_INSTANCE_DISAPPEARED`。
2. `breeding_enabled=false`：`INVENTORY_INSTANCE_DISABLED`。
3. 所有者或公会未解析：`INVENTORY_INSTANCE_UNRESOLVED`。
4. 已锁定且不允许复用：`INVENTORY_INSTANCE_LOCKED`。
5. 请求玩家自己的实例直接可用，关闭共享不影响本人使用。
6. 非本人实例仅在允许共享、同公会且 `share_enabled=true` 时可用；否则分别记录共享关闭、不同公会或全局关闭原因。

### 4.3 被动保留

期望被动用最多 4 位的位图表示。完成实例分配后，从最终目标向叶节点反向分派被动：

- 最终步骤要求全部期望被动。
- 每个被动必须由至少一个父分支可携带；不能凭空生成。
- 当两个分支都可携带时，穷举最多 `2^4` 个分派，选择中间检查点更少、单步要求更集中且稳定键更小的方案。
- 每个中间节点输出其 `required_passive_ids`；后续步骤只把满足该集合的子代视为可执行父母。
- 实例上的非目标被动只作为额外干扰量参与策略难度，不被描述为精确概率惩罚。

## 5. 限制、完成语义与候选数量

所有路线和实例组合共用一个展开预算，并使用注入式单调时钟检查硬超时。限制包括：

- `max_generations`，默认 5。
- `max_expanded_nodes`。
- 每个种类保留的路线状态数。
- 每个被动覆盖桶保留的实例分配状态数。
- 评分前最大候选数和最终输出数。
- `timeout_ms`。

枚举顺序完全稳定，因此节点限制和候选限制的部分结果稳定。超时只返回超时前已经完整校验和评分的候选，并明确标记搜索不完整；调用方不得把它解释成“全部合法路线”。

数量规则：

- 搜索完成且合法路线不少于 3 条时，至少返回 3 条可比较候选。
- 搜索完成且不足 3 条时返回全部合法路线，并给出 `FEWER_THAN_THREE_LEGAL_ROUTES`；0 条另给 `NO_LEGAL_ROUTE`。
- 命中任一限制时返回已完成候选和对应限制码，同时 `search_complete=false`，不声称已经返回全部合法路线。

## 6. 策略估计与综合评分

评分配置是代码中的不可变版本注册表，并与请求中的 `algorithm_version/scoring_profile_version/optimization_mode` 交叉校验。未知或错配版本稳定失败，不能回退到最新配置。

没有可信概率时，每一步只按以下可解释因素生成策略区间：

- 本步必须保留的目标被动数量。
- 真实父母携带的非目标被动数量。
- 是否需要中间子代的指定性别。
- 串行步骤数量。

总区间为各步骤策略区间之和；输出固定标记 `strategy_heuristic_no_verified_probability`。不得输出百分比、赔率或“精确成功率”。

每条路线固定计算七个 0～100 的正向组件：

1. `route_length`：代数和步骤越少越高。
2. `inventory_coverage`：真实库存父源占全部父源的比例。
3. `passive_concentration`：期望被动集中在更少起始载体时更高。
4. `borrowing`：唯一借用实例越少越高。
5. `intermediate_cost`：中间代和被动/性别检查点越少越高。
6. `attempt_cost`：策略尝试区间越低越高。
7. `stability`：替换敏感的借用、中间性别和多被动检查点越少越高。

四种模式只切换版本化整数权重，不改变合法性或原始指标。整数基点计算并在输出边界统一舍入，避免平台浮点排序差异。`score_breakdown` 对每种模式保存原始指标、七个组件、权重、加权贡献和总分。四套排名先在完整已评分候选池上计算；返回集合先纳入四种模式的唯一第一名，再按请求模式补足，因此不会把请求模式截断后的次优路线误标为“最快”或“最少借用”。“最高成功率”在产品命名上保留，但其基础值仍是上述策略难度代理，不是未验证概率。

## 7. 可复现性

以下内容全部进入路线键或结果摘要：

```text
规范化请求
+ 固定库存快照 ID
+ 固定游戏数据版本 ID
+ 固定游戏数据 content hash
+ 算法版本
+ 评分配置版本
+ 有效配方/实例/被动分派签名
+ 确定性诊断计数
```

集合在进入算法时排序，字典不参与隐式顺序，平分时使用完整稳定签名。运行耗时和峰值内存只属于外部 benchmark，不进入结果摘要。相同输入和版本在未触发墙钟超时时必须产生字节一致的规范结果。固定节点限制也可复现；墙钟超时结果明确为运行边界产物。

## 9. 性能基准

仓库脚本用固定种子生成明确标注为虚构的合成配方图与库存。基准在进程内使用 `perf_counter` 和 `tracemalloc`，输出单个规范 JSON：

```text
graph: pal_species / effective_recipes / inventory_instances
expanded_nodes: species / assignment / total
elapsed_ms
peak_memory_bytes
pruned: species_routes / assignment_states / duplicates
hit_limits
candidate_count
```

基准不是游戏事实或成功率验证；它只证明资源保护和算法实现的运行特征。
